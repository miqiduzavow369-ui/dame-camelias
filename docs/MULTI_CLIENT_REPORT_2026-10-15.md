Статус: подготовлена реализация для проверки в тестовой среде. Рабочий бот не обновлён. Полная готовность к внедрению не подтверждена: новая цепочка не запускалась в Cloudflare/Telegram/Playwright с настоящими сервисами. Автоматические тесты с имитацией внешних ответов этого не доказывают.

## Что изменено

- Кабинет владельца стал фабрикой `createCabinet(userId)`: один механизм проверки анкет, выбора аккаунта, оценок, отзывов, предпросмотра, согласия, подтверждений и навигации для всех пользователей. Текущий пользователь находится в отдельном замыкании; глобальной изменяемой переменной пользователя нет.
- Сохранены прежние ключи владельца. Личные данные клиентов находятся в собственных Durable Objects и ключах с Telegram ID. Архивы подтверждений, черновики отзывов, статусы публикаций и сохранённые данные разделены. Черновики оценок сохраняются отдельно для каждой анкеты; согласие при повторном открытии не переносится.
- Все сообщения направляются ID выбранного кабинета. Проверяются ID отправителя, ID приватного чата, авторизация, профиль, nonce и этап операции. Telegram WebApp проверяет подпись до маршрутизации и внутри обработчика формы.
- Проверка анкет, все приватные payload-запросы, stage и результаты Actions несут `user_id`. Клиент использует полный существующий механизм владельца, включая фото и карточки. Синтаксически правильная ссылка не означает проверку. Повторное открытие уже подтверждённой точной ссылки не запускает проверку снова.
- Операции кабинета сериализованы в отдельном DO пользователя. Приватные записи становятся авторитетными в DO; KV читается при первом обращении. Для владельца личные изменения зеркалируются в старые KV-ключи. Приватные операции и одноразовые разрешения не зависят от согласованности KV.
- Для оценок добавлен общий постоянный атомарный claim по аккаунту сайта, анкете и типу. Для отзывов сохранён общий существующий guard. Другому пользователю показывается только недоступность действия, без чужого текста и подтверждения. Глобальный дневной лимит остаётся общим по анкете, максимум два действия за московские сутки.
- Баланс показывает `available`, с учётом резервов. Резервирование и финальное списание остаются в прежнем DO `publication-credits:<ID>`. Успешный повтор settlement не увеличивает `spent`. Очередь settlement в DO повторяет только сверку реестра; публикацию она не запускает.
- При доказанном отклонении dispatch GitHub (401/403/404/422) резерв возвращается. При неопределённом исходе резерв и блокировка сохраняются до сверки. Автоматического повтора отправки нет.
- Подтверждённый результат обновляет архив/статус только после проверки доказательства и успешной доставки Telegram. Положительный ответ формы сайта сам по себе не означает завершённую проверку публикации.
- Длительные публикационные операции сохраняются отдельно по nonce. Поздний результат обрабатывает исходную операцию и не затирает новую навигацию. Повторный callback завершённой операции отвергается.
- У владельца добавлены «➕ Добавить клиента» и «👥 Клиенты»: создание через ID → PIN → количество → подтверждение, список клиентов, пополнение, установка доступного остатка, смена PIN, приостановка и восстановление. Каждый запрос проверяет владельца и авторизацию. Подтверждение связано с конкретной операцией, устаревшая кнопка не подтверждает другое действие.
- Новые PIN хранятся как PBKDF2-SHA256, 100000 итераций, индивидуальная случайная соль. Даже незавершённое административное действие не сохраняет открытый PIN. Пять неверных попыток вызывают блокировку на 15 минут. Смена PIN и изменение доступа отзывают сессию.
- Сохранены действующий legacy PIN и авторизация пробного клиента. После успешного ввода legacy PIN его запись обновляется до PBKDF2. Сохранённая анкета №698842 переносится из существующего списка. Если нет корректных проверенных сведений, ссылка сохраняется и предлагается фактическая проверка; подтверждение не выдумывается.
- Плашки загружаются байтами и отправляются multipart в Telegram. Проверяется ответ Telegram. Клиентские изображения защищены `protect_content`. При ошибке показывается чистый текст, без диагностических заглушек. При обычной навигации подтверждения публикаций из чата не удаляются.
- Исторические оценка и отзыв №652282 защищены от повторной отправки согласно паспорту восстановления. Старые кнопки ручного снятия блокировки в кабинете больше не разрешают эту отправку. Архивы не удаляются.

## Секреты и настройки

Используются прежние `BOT_TOKEN`, `WEBHOOK_SECRET`, `DC_ACTIONS_TOKEN`, `ANKETA_CALLBACK_TOKEN`, существующие секреты GitHub Actions для сайта и прокси. Значения не менялись и в отчёт не включены. Новый обязательный секрет не требуется.

Сохраняются имеющиеся `VISITORS_KV`, `ORDER_REMINDERS`, класс `OrderReminder` и его миграция. Новая инфраструктура/Telegram-бот не создаются.

Новые необязательные обычные переменные окружения:

- `CABINET_CLIENTS_ENABLED=false`: закрыть новые клиентские действия, сохранив обработку уже принятых результатов и read-only proof.
- `CABINET_PUBLICATIONS_ENABLED=false`: запретить новые финальные отправки и выдачу новых разрешений runner'ам, сохранив получение результатов.
- `CABINET_ACTIONS_REF`: по умолчанию `main`. Для теста в другой ветке нужен согласованный callback в совместимую тестовую среду. Нельзя направлять изменённый runner из ветки в старый рабочий Worker и считать это изолированным тестом.

Если переменные остановки не заданы, функции разрешены для авторизованных активных клиентов. Перед первым разрешённым развёртыванием явно выставить оба флага в `false` и открывать поэтапно.

## Безопасная остановка и откат

Основной обратимый откат после начала использования — установить оба флага в `false`, оставив совместимый обработчик callbacks и очередь settlement. Это останавливает новые действия, сохраняет результаты уже запущенных операций и не возвращает старую программу, которая не понимает новые корректировки баланса. Расходы, claims и историю не удалять, workflow публикации не перезапускать.

Возврат старого исходного кода возможен только после завершения всех runner'ов, сверки очередей и сохранения нового состояния. До открытия клиентов и до новых списаний можно вернуть точный прежний Worker/commit и согласованную версию workflow. После новых операций слепой откат к резервному коммиту небезопасен: старый код не обслуживает новые клиентские DO и не учитывает `adjustment` в реестре. Тогда сначала требуется совместимое исправление или отдельная проверенная миграция, сохраняя запрет отправок.

После периода работы на старом коде нельзя повторно включать новую версию с устаревшим авторитетным кешем владельца без сверки DO с изменившимися KV-ключами. Флаги остановки позволяют обойтись без такого несовместимого возврата кода.

## Ручная проверка владельцем после разрешённого внедрения

1. Войти владельцем и пробным клиентом с двух разных Telegram-аккаунтов. Сопоставить собственные анкеты и фактические остатки. Клиент не должен видеть административные кнопки или данные владельца.
2. Проверить плашки, фотографии, порядок дневной плашки и карточки анкеты, подпись обновления снизу, возврат в начало и сохранность подтверждений.
3. Добавить HTTPS-ссылку, получить фактический результат Actions, подтвердить правильные данные. Повторно открыть её, сменить домен, проверить устаревшие кнопки.
4. Сохранить разные тексты и оценки у двух пользователей/анкет, переключаться между ними, проверить отсутствие пересечений. Убедиться, что отправка требует нового согласия.
5. Через владельца создать клиента, изменить PIN/остаток, приостановить и восстановить доступ. Старые сессии и подтверждения административных действий должны перестать подходить.
6. При отдельно разрешённой реальной публикации проверить совпадение профиля, результата сайта и скриншота; ровно одно списание; повторный клик ничего не публикует. Анкету №652282 для этого не использовать.
7. Убедиться, что третий участник не может превысить общий дневной лимит одной анкеты, а после 00:00 МСК начинается новая дневная квота без отмены постоянных блокировок публикаций.

## Оставшийся блокер

Нет настоящего прогона новой цепочки GitHub Actions → Cloudflare → Telegram → сайт/Playwright в совместимой разрешённой среде и нет проверки runtime Cloudflare. Нет доступа к фактическому реестру для контрольной сверки живых балансов/данных. Поэтому полная готовность и соответствие реального интерфейса эталону пока не заявляются, разрешение на внедрение этим отчётом не запрашивается.

# DAME CAMELIAS — подготовка 30 изолированных мужских аккаунтов

## Статус
Это **подготовительная ветка**, НЕ готовая мультиаккаунтная интеграция. Никого кроме `yan_first` не включать. Никаких публикаций в ходе подготовки.

## Решения владельца (2026-10-18)
- 30 мужчин: Ян Первый ... Ян Тридцатый. 29 друзей передают отдельные аккаунты сайта и прокси. Друзьям НЕ требуются кабинеты Telegram.
- Управление всеми аккаунтами доступно только владельцу через 👑 ADMINISTRATION.
- Общий баланс кредитов клиента. Списания идентифицируют мужчину, не ломая имеющийся ledger.
- Через администратора можно заменить **IP/host прокси и порт**, оставив его логин/пароль прежними. До переключения обязательно проверить соединение и ожидаемый IP. При неуспехе сохранить старую конфигурацию.
- Сохранить все текущие UX, соглашение, модерацию, архив, скриншоты, лимиты и защиту от дублирования.

## Совместимость
- Сохраняем `yan_first` и `yan_second` как уже существующие идентификаторы; остальные `yan_03` ... `yan_30`.
- В `src/man_accounts.js` создан **неподключённый** реестр имён. `enabledByDefault` истинно только для первого.
- Существующий `ACTIVE_ACCOUNT = "yan_first"` до решения по полностью изолированному маршруту не менять.
- Записи с отсутствующим account считать принадлежащими первому только при проверенном legacy происхождении. Иначе ошибка и ручная проверка.

## Обязательные серверные проверки до подключения
1. Полная трассировка accountId от Telegram initData до серверного разрешения, workflow_dispatch, браузера, callback, KV, DO, proof и history. Нельзя доверять accountId только из UI.
2. Раздельные секреты и аккаунты сайта; отдельные браузерные контексты. Проверка личности **после входа**, а не только successful login.
3. Изоляция KV по (telegramUserId, accountId, profileId), включая выбор, черновики, тикеты, workflow, callback nonce, модерацию и proof.
4. Глобальные запреты сайта и повторных публикаций оставить глобальными. Любые неизвестные правила = fail-closed.
5. Списания/резервы кредитов атомарные, идемпотентность операций и отсутствие повторной отправки при timeout.
6. Панель ADMINISTRATION доступна только owner; клиентский API никогда не возвращает токены, cookies, пароли прокси или логины сайта.
7. Параметры прокси менять серверной **атомарной операцией**: валидация -> проверка нового IP -> новая версия маршрута -> переключение аккаунта. При ошибке старый маршрут остаётся. Смена host не должна изменять password.
8. Учётные данные не хранить в plaintext KV; дизайн защищённого хранилища и взаимодействия Worker/Actions согласовать до изменений.

## Гейт готовности
Нельзя включать нового мужчину до полного матричного прогона: выбор мужчины + выбор анкеты; ratings catalog и >=20% услуг; черновик; предварительная проверка; явное подтверждение; публикация; проверка proof; отзыв + админ модерация + отклонение/корректировка; лимиты и кредиты; история; разграничение прав; отказ неправильного account/proxy; конкурентные операции. Первичная проверка второго — только чтение.


## Утверждённый порядок: секреты и прокси в самом конце (2026-10-18)
- Сейчас **не запрашивать, не вводить, не переносить и не менять** реальные логины, пароли, токены, proxy-host, proxy-port, proxy-user, proxy-password, expected IP или другие секреты ни в GitHub, ни в Cloudflare, ни в Telegram.
- Сначала создать и протестировать серверную модель 30 аккаунтов, защиту Яна Первого, изолированные состояния, глобальные ограничения, историю и архитектуру UI.
- В 👑 ADMINISTRATION предусмотрен раздел «Мужские аккаунты» с карточками 01–30 и формой для **последующего** ввода логина/пароля сайта и прокси по конкретному мужчине. Пока поля могут иметь статусы «Не настроено» и «Подключить позднее», а операции, требующие секретов, должны fail-closed. Не сохранять секреты в браузере или обычном KV.
- Отдельно предусмотреть редактирование IP/адреса и порта прокси без смены существующих прокси-логина и прокси-пароля; замена не должна вступать в силу до проверки нового адреса, IP и маршрута. Показ секретов и возврат секретов из API запрещены.

GitHub Actions secrets сами по себе не предоставляют API для безопасного чтения существующего пароля, поэтому нельзя обещать редактирование в админке по модели «прочитать/переписать GitHub secret».
- На финальном этапе выбрать безопасный путь подачи секретов в GitHub Actions / Cloudflare и провести подключение 29 аккаунтов; никаких реальных секретов в репозиторий, код, коммиты, логи или chat.
- Не активировать Янов 02–30 до завершающей настройки, проверки логина, прокси, внешнего IP и отдельного разрешения владельца.

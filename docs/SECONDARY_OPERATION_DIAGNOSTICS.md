# ADMIN: диагностика персональной операции мужчины

## Защищённое чтение

`POST /api/admin` (использовать существующий адрес ADMIN API приложения и авторизацию через подписанный Telegram Mini App initData; никакого отдельного публичного просмотра).

Параметры действия: `action: "secondary_operation_status"`, `userId` (ID клиентки), `accountId` (например `yan_second`), `profileId` (ID анкеты), `kind` (`rating` или `review`) и `nonce` (12 шестнадцатеричных знаков).

Запрос обслуживается **только после проверки полномочий ADMIN**. Показана операция конкретной клиентки. Не возвращаются пароль, прокси, HMAC-ключ, одноразовый токен callback, исходный текст или Telegram file_id.

## Значение статусов

| Поле | Смысл |
|---|---|
| `publicationStatus: not_started` | Отправка для указанной операции не начиналась |
| `publicationStatus: prepared` | Предварительная блокировка выполнена; публикация на сайте не доказана |
| `publicationStatus: attempted` | Попытка внешней отправки уже была зафиксирована; повторный POST запрещён |
| `publicationStatus: uncertain` | Результат внешнего сайта не подтверждён, требуется ручная проверка |
| `ticketStatus: issued` | Создан одноразовый билет для результата |
| `ticketStatus: consumed` | Билет был погашен; это **не** подтверждение публикации |
| `resultStatus: proof_saved` | Сохранены метаданные подтверждения и ID скриншота; кредит ещё не завершён |
| `resultStatus: reconciliation_required` | Нужно вручную сверить доказательство и/или атомарный реестр |
| `creditStatus: reserved` | Кредит зарезервирован, но ещё не завершён |
| `creditStatus: settling` | Результат завершения кредита неопределён |
| `completed: true` | Только при одновременном подтверждении операции, доказательства и кредита |
| `needsReview: true` | Состояние требует внимания оператора; не выполнять повторную публикацию |
| `canRetrySitePost: false` | Диагностика никогда не предлагает автоматически повторять публикацию |
| `publicationEnabled: false` | Этот экран не открывает доступ к настоящему исполнителю |

## Сценарий ручной сверки

1. Найти конкретную клиентку, анкету, мужчину и nonce операции.
2. Проверить технический результат браузерного задания, сайт Intimcity, статус и подлинность доказательства.
3. Сопоставить результат со статусом кредитного ledger. **Не повторять POST на Intimcity.**
4. Если данные расходятся, оставить операцию заблокированной и документировать причину.
5. Только после отдельного проверенного механизма ручного восстановления в финансовом реестре возможно завершение или освобождение резерва.

## Изоляция и ограничения

- Запись клиента `123456789` нельзя использовать для чтения операций другого клиентского Durable Object.
- `yan_first` не участвует в этом маршруте.
- Для `yan_second`—`yan_30` используются те же этапы, но независимые ключи.
- Текущий код только предоставляет **read-only** диагностический API; графическое представление в ADMIN ещё не подключено.
- Сквозная публикация, персональный Chromium исполнитель и защищённая выдача билета runner остаются не подключёнными. PR #207 не следует считать production-ready.
